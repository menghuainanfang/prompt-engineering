## 1. 产品定位和硬边界

长期愿景：个人生活管理平台。当前仅迭代阅读模块，不开发天气、日历、日记、饮食、运动、作息、云同步、AI 记忆或社交功能。

必须维护原定的完整阅读闭环：
书架与电子/纸质书 → PDF/EPUB 阅读 → 高亮/键盘批注/PDF 鼠标绘制 → 每本书置顶总心得 → 多篇阅读日志 → 观点卡片 → 实践反馈 → 月年阅读计划与统计。

总心得始终是书籍主页视觉核心。批注和笔记保持可定位的双向来源关联。所有功能坚持本地优先、离线可用、用户数据独立、无账号要求。不得用演示卡片替代真实数据。

## 3. 第二步：真正审计开源成果，允许大胆复用

打开并核验下列官方仓库的当前 README、许可证、依赖、近期待维护状态、安装/运行步骤和相关源代码。不得只凭搜索摘要决定使用。优先使用成熟库解决通用问题，不重复造轮子。

### 高优先级：直接依赖或组件复用候选

- PDF.js：https://github.com/mozilla/pdf.js — PDF 渲染和注释基础；验证当前项目兼容性与授权。
- epub.js：https://github.com/futurepress/epub.js — EPUB 阅读、CFI 和文字高亮。
- foliate-js：https://github.com/johnfactotum/foliate-js — 多格式阅读候选；明确 API 不稳定及版本固定风险。
- React PDF Highlighter Extended：https://github.com/DanielArnould/react-pdf-highlighter-extended — 文本与区域批注候选，需验证实际集成与维护情况。
- Tiptap：https://github.com/ueberdosis/tiptap — 仅评估符合需求的开源核心及许可适用扩展。
- shadcn/ui：https://github.com/shadcn-ui/ui — 可复用交互组件；其默认样式不是最终视觉方案。
- Mantine：https://github.com/mantinedev/mantine — 作为互斥候选，不要把多个 UI 框架全部装入项目。

### 高优先级：完整 Fork、上游功能复用或产品交互研究

- Readest：https://github.com/readest/readest — 现代书架、多格式阅读、排版/主题/专注模式，完整 Fork 优先评估对象。
- Koodo Reader：https://github.com/koodo-reader/koodo-reader — 书架、阅读、备份和笔记系统；完整 Fork 备选。
- Foliate 桌面应用：https://github.com/johnfactotum/foliate — 安静的阅读 UI，主要是视觉和交互研究，不等于可直接嵌入的 foliate-js。
- Zotero 阅读器说明：https://www.zotero.org/support/pdf_reader — 批注转笔记、来源跳转、研究型密集界面。
- BookLore：https://github.com/booklore-app/booklore — 书库视觉、封面排列和元数据工作流，默认不引入其服务器架构。

为 Readest、Koodo、保留现有外壳 + 组件集成三条路径制作事实驱动的对比表：功能覆盖、可复用代码边界、上游维护频率、技术栈吻合度、数据迁移成本、打包复杂度、可访问性、安全、许可证义务、后续持续同步上游更新的成本、视觉控制权。

对值得考虑的路线在临时目录做小型技术验证，能够运行时分别截图；严禁凭 README 夸大集成效果。评估后写 docs/V02_OPEN_SOURCE_DECISIONS.md，并做出单一推荐及被否决方案的理由。

**决策门槛：只有在存在可量化、显著的工程收益，数据迁移可逆、核心功能通过回归测试、许可证可合规执行时才迁移或 Fork 整体项目；否则保留现有程序，局部复用成熟组件。** 不允许为了提高“代码复用率”而增加维护负担。

### 开源合规

逐一确认实际拷贝代码、依赖、图标、插画、封面示例和字体的许可。MIT/BSD/Apache 不是零义务；保留版权声明和 NOTICE。Readest、Koodo、BookLore 等 AGPL 项目可以依法 Fork 与分发，但需审查对应衍生作品的许可证、源码提供及保留声明等义务；Foliate 桌面应用与 foliate-js 的许可证不同。若采用强 copyleft 路线，先输出具体合规方案交用户确认。不得移除上游署名、冒用原产品商标，也不得默认复用上游品牌图形或未经授权的书封面资产。

生成/更新 THIRD_PARTY_NOTICES、LICENSE 信息、来源清单与改动记录。鼓励将通用修复提交上游，但不得未经授权发 PR 或公开泄露个人资料。

## 4. 美术方向：Quiet Reading / Editorial Minimalism

目标不是像网站模板一样“时尚”，而是像经得起长时间使用的优雅数字书房。美术风格由 Foliate 的安静、Readest 的沉浸、Zotero 的信息组织与 BookLore 的藏书秩序共同启发，但必须形成 ReadingOS 的独立身份。

### 基础设计语言

- 气质：书卷气、清晰、安静、温暖而不过度复古；长期使用时眼睛舒适。
- 层级：正文与用户心得为主角；工具栏、标签和统计是辅助，不与正文争夺注意力。
- 色彩建议作为起点而非机械套用：纸白 #F5F2EC、暖灰 #E9E3D8、墨黑 #242925、松绿 #526554、铜棕 #A77A53、高亮黄 #DCC776。按 WCAG 对比度和真实屏幕调优，提供独立深色方案。
- 字体：界面使用可靠的 Windows 系统无衬线中文字体回退；在书名/文章标题处节制使用宋体或合适的开源衬线字体；绝不在仓库中擅自打包或再发布商业字体。PDF 内容尊重原书排版，EPUB 字体由阅读器设置独立控制。
- 间距采用 4/8/12/16/24/32 的一致节奏；卡片圆角克制（大致 6–10px）；尽量使用边框、留白、色调分层而非大面积阴影。
- 优先使用真实书封面自然宽高比，缺封面的书使用高质量排版占位而不是随意 AI 图片。
- 统一标题、正文、辅助信息、时间戳、链接、按钮和状态文字层级；灰色小字仍必须易读。

### 明确禁止模板化 AI 风格

避免全屏渐变、玻璃拟态、泛滥的大圆角悬浮卡、每个区域都配彩色图标、无意义的 KPI 大数字、随机 emoji、默认 shadcn 演示页观感、过度动画、没有功能理由的背景纹理、为追求高级而降低可读性。

**不要把安装 shadcn/ui 或改变 CSS 变量等同于美术设计。** 请先对真实页面分析内容层次、密度和空间，再建立 Design Tokens 和经过统一处理的组件样式。

### 四个必做场景

1. 书房：以书封面和书名作为视觉锚点；导入、搜索、筛选自然易找；支持网格/列表；空状态高质量但不喧宾夺主。
2. 书籍主页：置顶总心得须立即可见；继续阅读容易找到；日志、观点和实践显著分组；避免所有信息被卡片包围。像一本可以不断修改的私人读书档案。
3. PDF/EPUB 阅读器：正文居中，控制可收起；目录、批注、笔记侧栏的开合平稳；高亮颜色可辨且不刺眼；鼠标默认选字，绘画需显式激活。尊重 EPUB 重排和 PDF 固定页面。
4. 心得编辑器与批注侧栏：提供足够大的内容区，轻量格式工具，自动保存状态清楚；从原文批注引用到日志/观点并返回来源，操作路径短且可理解。

导出 docs/ART_DIRECTION.md、docs/DESIGN_TOKENS.md、docs/COMPONENT_RULES.md，具体说明版式、字体回退、颜色、间距、圆角、边框、动效和禁止用法。

## 5. 交互质感优先于装饰

逐屏清理：重复入口、无效按钮、模糊命名、多层嵌套弹窗、图标无 tooltip、误触、无法撤销、保存状态不可见、空态和报错处理不足。

阅读工作流应尽量少点击：书架继续阅读；选区后高亮/写批注；批注引入日志；日志提炼观点；观点记录实践。为上述流程定义实际可测的操作步数基线，优化后重新测量，而不是随意声明“更流畅”。

关键要求：键盘 Tab 与 focus 可见；快捷键不与文字编辑冲突；缩放 125%/150% 不截断主要按钮；支持 1280×720、1366×768、1920×1080 三类桌面窗口；遵循系统减少动态效果设置；文字与背景对比度以 WCAG AA 为目标；动画只用于状态衔接，不影响速度。

不能牺牲用户自定义阅读背景和高亮配色；每本书的阅读偏好持久化，不污染其他书籍。

## 6. 分阶段完成真实开发

### Phase A：审计及设计决策
先记录 v0.1 baseline、真实界面截图、开源评估表和清晰的视觉方案。提出 2 个经过实际参考验证的视觉候选（例如浅色纸张式与偏理性的学术式），比较信息密度和阅读舒适度，选一套主风格实施；无需长时间等用户审美确认才能开始非破坏性优化。

### Phase B：可运行的视觉纵向切片
先完成一个真实的“书房 → 书籍主页 → 阅读器 → 批注/心得”路径，不制造孤立的 Figma 风格展示页面。保持真实数据库读写与原有功能，并保存 before/after 对比截图。

### Phase C：深度集成与稳定性
仅在已通过小验证并明确依赖边界时集成开源组件。任何替换阅读器的变更都要做书籍导入、EPUB 锚点、PDF 坐标、手写路径、批注链接、书签/进度和备份恢复的回归测试。每阶段保持可构建、可回滚的 Git 提交。

### Phase D：质量与交付
完善所有关键页面、深浅色、空态、错误反馈、键盘可达性与打包。验证 Windows 安装程序及离线能力。朋友测试版要有明确的安装说明、数据目录、已知问题、反馈入口和版本号。

## 7. 明确验收门槛

至少做出下面这些可核验结果（未测试写未测试）：

- A. 原有 v0.1 的 P0 功能没有倒退，旧数据库可打开且保留所有书籍、总心得、日志、批注、观点和实践数据。
- B. PDF 选区、文字批注、鼠标绘画、坐标定位在缩放/重启后保持可靠；EPUB 高亮在字号变更后仍能定位。
- C. 关闭重开阅读进度、保存笔记、导出、备份→恢复演练通过；真实书籍原件不被覆盖。
- D. 书房、书籍主页、阅读器、编辑器四个场景都有同条件 before/after 截图与具体设计评审结论。
- E. 暗色、亮色、窄窗口和高 DPI/系统缩放下不出现主要文字裁切、横向溢出或不可操作控件。
- F. 选字→高亮、批注→日志引用、日志→观点、观点→实践可由实际交互走通；来源定位失效时不错误跳转。
- G. 所有新增第三方代码、字体、图标都有许可证据和第三方声明；公开仓库不含私人数据库、真实用户书籍或 API 密钥。
- H. 可在 Windows 生成安装包；若无法在当前环境安装验证，必须区分“源码构建成功”“安装包生成”“实际安装验证”三级事实。
- I. 新视觉不是由一组通用 AI 风格的示范卡片组成，而是统一的字体、层级、密度、边距、动作和状态系统；给出截图对照与自我批判记录。
